# Inspool Wiki 유지·관리 규칙

본 파일은 `inspool-wiki-zh/` 실험 구역의 유일한 규칙 진입점으로, 에이전트가 이 지식베이스를 관리하는 방법을 안내합니다.

## 핵심 목표

산발적인 원본 자료를 구조화되고, 교차 참조가 가능하며, 지속적으로 진화하는 wiki로 점진적으로 축적합니다.

에이전트의 역할은 임시로 질문에 답하는 것이 아니라, 지식 구조 자체를 유지·관리하는 것입니다.

## 언어 기본값

- 사용자의 기본 언어는 한국어입니다.
- 사용자가 명시적으로 다른 언어를 요청하지 않는 한, 에이전트가 생성·업데이트·정리하는 문서는 모두 한국어로 작성합니다.
- 이 규칙은 페이지 본문, 설명 문서, 인덱스, 로그, 명령어 템플릿 모두에 적용됩니다.
- raw 원본 자료는 원래 언어를 유지해도 됩니다 (강제 번역 불필요). 단, wiki 축적 계층의 설명과 구조는 기본적으로 한국어를 사용합니다.

## 3계층 구조

### 1. `raw/`

- 웹 클리핑, 아티클, 도서 발췌, 회의록, PDF 변환본, 스크린샷 설명 등 원본 자료를 보관합니다.
- 이것이 사실 소스 계층입니다.
- 본문은 기본적으로 읽기 전용입니다.
- 기본적으로 두 가지 흐름 관련 변경만 허용합니다: 파일 경로 이동, 소량의 frontmatter 처리 메타데이터 업데이트.
- 사용자가 명시적으로 요청하지 않는 한, `raw/` 내 본문 내용을 재작성·삭제·수정하지 않습니다.

### 2. `wiki/`

- 에이전트가 관리하는 구조화된 지식 페이지를 보관합니다.
- 에이전트가 생성, 업데이트, 이름 변경, 교차 링크를 할 수 있습니다.
- 사용자 질문에 답할 때 여기서 먼저 읽고 종합합니다.

### 3. `AGENTS.md`

- 구조 규칙, 페이지 표준, 운영 절차, 품질 기준을 정의합니다.
- 실제 운영 중 더 나은 방식을 발견하면 사용자 동의 후 이 파일을 진화시킬 수 있습니다.

## 디렉토리 규칙

### `raw/`

- `raw/unprocessed/`: 처리 대기 중인 새 자료
- `raw/processed/`: ingest 완료된 자료
- `raw/assets/`: 원본 자료에서 저장한 이미지, 첨부 파일, 기타 정적 리소스
- `raw/index.md`: 자료 처리 상태 인덱스

### `wiki/`

- `wiki/sources/`: 개별 소스의 요약 페이지
- `wiki/entities/`: 인물, 조직, 제품, 프로젝트, 도구 등 엔티티 페이지
- `wiki/concepts/`: 개념, 방법론, 프레임워크, 용어 페이지
- `wiki/synthesis/`: 주제별 종합, 비교 분석, 단계적 결론, 질문·답변 축적
- `wiki/meta/`: 개요, 규칙 설명, 주제 경계, 유지관리 기록 등 메타 정보
- `wiki/index.md`: 내용 인덱스
- `wiki/log.md`: 시간순 로그

참고:

- 사용자가 `wiki/concepts/`, `wiki/entities/`, `wiki/synthesis/` 아래에 분류용 서브폴더를 직접 만들 수 있습니다.
- 이러한 서브폴더는 사용자가 관리하는 조직 계층이므로, 에이전트는 이를 안정적이고 불변하는 의미론적 사실로 간주해서는 안 됩니다.
- 에이전트는 기본적으로 이 디렉토리들 아래의 모든 수준의 서브폴더와 호환되어야 합니다.

## 페이지 작성 원칙

- 기본적으로 한국어로 작성합니다 (사용자가 다른 언어를 명시적으로 요청하지 않는 한).
- 명확한 제목과 짧은 단락을 사용합니다.
- Obsidian 스타일 이중 링크를 최대한 사용합니다: `[[개념 이름]]`.
- 중요한 사실에는 소스 페이지 참조를 추가합니다.
- 사실, 판단, 추측을 구분해서 작성합니다.
- 자료 간 충돌이 있을 경우 명시적으로 기록하고 조용히 덮어쓰지 않습니다.

## 사용자 관리 분류 디렉토리

- 사용자가 `wiki/concepts/`, `wiki/entities/`, `wiki/synthesis/` 아래에 서브폴더를 만들고 페이지를 이동하여 분류할 수 있습니다.
- 에이전트는 이 행동을 비정상 상태가 아닌 정상적인 유지관리 동작으로 취급해야 합니다.
- 페이지 유형은 최상위 디렉토리(`concepts / entities / synthesis`)로 결정되며, 더 깊은 서브폴더 이름으로 결정되지 않습니다.
- 더 깊은 서브폴더는 주로 사용자 자신의 주제 정리를 위한 것이므로, 에이전트는 이 경로에 과도하게 의존하여 지식 관계를 추론해서는 안 됩니다.
- 사용자가 명시적으로 요청하지 않는 한, 에이전트가 임의로 이 분류 디렉토리를 재구성하지 않습니다.
- 에이전트가 페이지를 읽고, 업데이트하고, lint할 때 이 디렉토리들 아래의 모든 서브폴더를 재귀적으로 스캔해야 합니다.

## 경로 안정성 규칙

- `wiki/concepts/...`, `wiki/entities/...`, `wiki/synthesis/...`의 전체 파일 경로를 지식 의미론의 일부로 하드코딩하지 않습니다.
- 본문과 frontmatter에서는 Obsidian wiki 링크를 우선 사용하고, 순수 경로 문자열에 의존하지 않습니다.
- `[[페이지 이름]]` 또는 `[[상대적으로 안정된 wiki 링크]]`로 표현할 수 있을 때는 일반 텍스트 경로를 사용하지 않습니다.
- 사용자가 페이지를 새 분류 서브폴더로 이동했을 때, 에이전트는 이를 합법적인 상태로 인식하고 정상적으로 계속 작동해야 합니다.
- 분류 이동 후 오래된 경로 참조가 발견되면, 사용자에게 디렉토리 구조를 되돌리라고 요청하기보다 오래된 경로 참조를 먼저 수정합니다.
- `raw/unprocessed/`에서 `raw/processed/`로의 이동은 흐름 이동이며, 안정적인 경로가 아닙니다.
- 따라서, 소스 페이지의 `raw_note`, 본문의 "원본 자료" 링크, 기타 명시적 raw 경로는 approve 후 raw의 현재 위치로 동기화하여 수정해야 합니다.

## 증거 노드와 그래프 원칙

- `wiki/sources/` 내 페이지는 그래프의 증거 노드입니다.
- `wiki/entities/`, `wiki/concepts/`, `wiki/synthesis/`는 지식 노드입니다.
- 지식 페이지의 핵심 결론은 외부 URL로 직접 링크하는 대신 로컬 `sources` 페이지로 링크를 우선합니다.
- 외부 URL은 주로 raw 파일 frontmatter와 소스 페이지 "소스 정보"에 보존하며, 주요 그래프 엣지로 사용하지 않습니다.
- 소스 페이지의 특정 단락을 정확히 가리킬 수 있다면 앵커가 포함된 링크를 우선 사용합니다: `[[sources/어떤 소스#핵심 관점]]`.
- 결론이 여러 소스에서 온 경우 여러 증거 노드를 연결할 수 있습니다.
- 결론에 충돌하는 소스가 있다면 `contradicts` 필드와 본문의 "이견과 충돌" 섹션에 명시적으로 기록해야 합니다.

## 관계 필드 규칙

Obsidian Graph와 Dataview를 모두 지원하기 위해 페이지는 다음을 동시에 관리해야 합니다:

1. 본문의 명시적 이중 링크
2. frontmatter의 구조화된 관계 필드

권장 frontmatter 필드:

- 공통 필드:
  - `type`
  - `status`
  - `topic`
  - `updated`
- 소스 페이지 우선 필드:
  - `raw_note`
  - `external_url`
  - `related_entities`
  - `related_concepts`
  - `related_sources`
- 엔티티 페이지, 개념 페이지, 합성 페이지 우선 필드:
  - `supports`
  - `contradicts`
  - `related_entities`
  - `related_concepts`
  - `related_sources`
  - `related_synthesis`

필드 값은 로컬 wiki 링크를 우선 사용합니다: `[[sources/어떤 소스]]`.

## 인용 및 링크 규칙

- 핵심 결론, 구체적 사실, 숫자, 논쟁적 판단에는 가능한 한 증거 링크를 추가합니다.
- 본문의 증거 링크는 `[[sources/...#어떤 섹션]]`을 우선 사용합니다.
- frontmatter의 `supports`와 `contradicts`는 최소한 페이지 수준의 소스 노드로 링크해야 합니다.
- 현재 충분한 증거가 없다면 `supports`에 억지로 쓰지 말고 "확인 필요"로 표시합니다.
- 지식 페이지 본문에 외부 URL을 대량으로 나열하지 않습니다; 로컬 소스 페이지 링크로 변환을 우선합니다.

## Raw 흐름 메타데이터

에이전트가 raw 파일 frontmatter에 소량의 흐름 필드를 관리하여 이후 ingest의 컨텍스트 부담을 줄일 수 있습니다.

권장 필드:

- `processing_status`: `unprocessed`, `pending_review`, 또는 `processed`
- `reviewed_at`: 사용자 확인 날짜
- `processed_at`: 처리 완료 날짜
- `processed_into`: 해당 자료에서 파생된 wiki 페이지 경로 (소스 페이지 경로 우선)
- `ingest_group`: 선택 사항. 여러 관련 raw 파일을 같은 배치로 명시적 그룹화

제약:

- 이 필드들은 흐름 메타데이터이며, 소스 본문이 아닙니다
- 이 필드들의 생성·업데이트는 허용됩니다
- 이를 이용해 원본 자료의 본문 내용을 변조하는 것은 허용되지 않습니다

## 페이지 권장 구조

모든 페이지가 완전히 일치할 필요는 없지만, 다음 구조를 우선 따릅니다.

### 소스 페이지 `wiki/sources/`

권장 포함 내용:

- 소스 정보
- 핵심 요약
- 주요 관점
- 증거 발췌
- 추출 가능한 엔티티
- 추출 가능한 개념
- 기존 wiki와의 연결
- 확인 필요 질문
- 관련 소스

### 엔티티 페이지 `wiki/entities/`

권장 포함 내용:

- 한 줄 정의
- 배경
- 핵심 속성
- 지지 증거
- 이견과 충돌
- 관련 이벤트 또는 관점
- 관련 개념
- 관련 소스
- 미해결 질문

### 개념 페이지 `wiki/concepts/`

권장 포함 내용:

- 정의
- 핵심 메커니즘
- 인접 개념과의 차이
- 지지 증거
- 반례 또는 한계
- 관련 엔티티
- 관련 소스

### 합성 페이지 `wiki/synthesis/`

권장 포함 내용:

- 주제 설명
- 결론 요약
- 지지 증거
- 이견과 충돌
- 현재 판단
- 열린 질문
- 후속 제안
- 관련 소스

## 소스 인용 규칙

- 중요한 결론 뒤에는 소스 페이지 링크를 추가합니다: `참조 [[sources/어떤 아티클]]`.
- 특정 단락을 가리킬 수 있다면 우선적으로 사용: `참조 [[sources/어떤 아티클#핵심 관점]]`.
- 결론이 여러 소스에서 온 경우 여러 관련 소스를 나열할 수 있습니다.
- 현재 소스를 확인할 수 없다면 확정적 사실로 쓰지 않고 "확인 필요"로 표시합니다.

## 3가지 핵심 작업

### 1. Ingest

사용자가 새 자료 처리를 요청할 때:

1. `raw/unprocessed/` 우선 스캔
2. 다음 ingest 단위를 선택 (기계적으로 한 파일만 선택하지 않음)
3. `raw/index.md` 읽기
4. 해당 소스의 핵심 정보 읽고 추출
5. 해당하는 소스 요약 페이지를 생성 또는 업데이트하고 그래프에 증거 노드로 연결
6. 관련 엔티티 페이지, 개념 페이지, 합성 페이지를 업데이트하고 `supports`, `contradicts`, 관련 이중 링크를 보완
7. `wiki/index.md` 업데이트
8. `wiki/log.md`에 기록 추가
9. 해당 ingest 단위 내 raw 파일들의 흐름 메타데이터를 업데이트하여 상태를 `pending_review`로 변경
10. `raw/index.md` 업데이트
11. 이번 ingest가 완료되었음을 사용자에게 명확히 알리고 사용자 확인을 기다림

단일 ingest는 요약 페이지 하나만 생성해서는 안 됩니다. 필요한 경우 여러 관련 페이지를 동시에 업데이트해야 합니다.

wiki 업데이트, 로그 업데이트, raw/index 업데이트가 모두 성공한 후에만 raw 파일 상태를 `pending_review`로 변경할 수 있습니다.

Ingest 단계에서 raw 파일을 직접 `processed/`로 이동하는 것은 금지됩니다. `unprocessed/`에서 `processed/`로의 이동은 사용자 확인 후에만 가능합니다.

### 1b. Approve

사용자가 "이번 ingest는 괜찮으니 processed로 아카이브해도 된다"고 명확히 표현할 때:

1. `raw/unprocessed/` 내 `pending_review` 상태의 ingest 단위 스캔
2. 사용자가 방금 확인한 그룹 선택; 사용자가 지정하지 않은 경우 가장 최근에 `pending_review`로 진입한 그룹 우선
3. 해당 wiki 페이지와 `raw/index.md` 기록이 존재하는지 재확인
4. 그룹 내 각 raw 파일의 이전 경로, 대상 새 경로, `processed_into` 기록
5. 그룹 내 각 raw 파일의 `processing_status`를 `processed`로 업데이트
6. `reviewed_at` 기록
7. 필요하다면 `processed_at` 보완
8. 해당 ingest 단위 내 raw 파일들을 `raw/processed/`로 이동
9. 이 raw들을 참조하는 wiki 내 오래된 경로 동기화 수정 (최소한 소스 페이지 frontmatter의 `raw_note`와 본문의 "원본 자료" 링크 포함)
10. 해당 배치 raw에 대한 로컬 자체 검사 수행, `wiki/` 내에 해당하는 오래된 `raw/unprocessed/` 경로 문자열이 더 이상 존재하지 않는지 확인
11. `raw/index.md` 업데이트
12. `wiki/log.md`에 `approve` 로그 추가

Approve 단계에서 사용자가 확인 시 명확하게 수정을 요청하지 않는 한, wiki 본문을 대폭 재작성해서는 안 됩니다.

10단계 로컬 자체 검사가 통과되지 않으면, 이번 approve를 완전히 완료된 것으로 간주해서는 안 됩니다. 잔여 경로를 명확히 보고하고 계속 수정하거나 중단해야 합니다.

### Ingest 단위 판정 규칙

기본 처리 단위는 "다음 처리 대기 그룹"이며, 판정 우선순위는 다음과 같습니다:

1. `raw/unprocessed/` 아래에 서브폴더가 있는 경우, 같은 서브폴더 내 파일들을 하나의 ingest 단위로 우선 처리
2. 여러 raw 파일이 동일한 `ingest_group`을 가진 경우, 해당 그룹을 하나의 ingest 단위로 처리
3. 사용자가 이 몇 개 자료를 함께 처리해야 한다고 명확히 밝힌 경우, 이들을 하나의 ingest 단위로 처리
4. 명확한 그룹화 신호가 없는 경우, 기본적으로 각 파일을 하나의 ingest 단위로 처리

### 배치 ingest 제약

- 배치 ingest는 명확히 관련된 소규모 자료 그룹에 적합합니다
- 단일 배치는 2~5개를 권장합니다
- 그룹이 5개를 초과하면 여러 소규모 배치로 나누어 컨텍스트 과부하를 방지합니다
- 배치 ingest 완료 후 그룹 내 각 raw 파일의 흐름 메타데이터를 개별적으로 업데이트해야 합니다
- `processed/`로 이동할 때는 그룹 전체를 이동하여 일부 처리·일부 미처리 상태 분열을 방지합니다

### 2. Query

사용자가 질문할 때:

1. `wiki/index.md` 우선 확인
2. 관련 페이지 읽기
3. 기존 wiki를 기반으로 종합 답변
4. 핵심 판단 답변 시 로컬 소스 페이지를 우선 인용하고, 필요 시 소스 페이지 앵커 사용
5. 답변이 장기적 가치를 지닌다면, 사용자 동의 또는 명확한 맥락에서 `wiki/synthesis/` 페이지로 역기록
6. 역기록 후 `wiki/index.md`와 `wiki/log.md` 업데이트

### 3. Lint

wiki를 정기적으로 건강 검사하며, 다음에 집중합니다:

- 고립된 페이지가 있는가
- 소스 근거 없는 강한 결론이 있는가
- 새 자료에 의해 반증되었지만 업데이트되지 않은 오래된 결론이 있는가
- 자주 언급되지만 아직 독립 페이지가 없는 개념이나 엔티티가 있는가
- 교차 링크가 명백히 부족한 페이지가 있는가
- 중복 페이지나 이름 불일치가 있는가
- 로컬 소스 페이지를 거치지 않고 외부 URL에 직접 의존하는 지식 페이지가 있는가
- 핵심 관계 필드 `supports` / `contradicts`가 없는 핵심 페이지가 있는가
- frontmatter에만 관계가 있고 본문에 명시적 이중 링크가 없는 페이지가 있는가
- 사용자 분류 이동 후 잔여 오래된 경로 문자열 또는 무효 디렉토리 가정이 있는가
- `raw/index.md`가 `raw/unprocessed/`와 `raw/processed/`의 실제 상태와 일치하는가
- `pending_review` 상태로 오래 머물고 있는 raw 자료가 있는가
- 함께 처리해야 하는데 분리된 관련 raw 자료가 있는가
- 배치가 너무 커서 컨텍스트 노이즈가 높은 ingest 그룹이 있는가

Lint 완료 후 결과를 `wiki/log.md`에 기록합니다.

## 인덱스 규칙

`wiki/index.md`는 목차 뷰이며, 본문 페이지가 아닙니다.

최소한 다음 정보를 관리해야 합니다:

- 각 중요 페이지의 링크
- 각 페이지의 한 줄 설명
- 선택적 주제 그룹
- 선택적 소스 수 또는 업데이트 날짜

질문에 답하기 전, `wiki/index.md`에서 관련 페이지를 먼저 찾습니다.

`raw/index.md`는 흐름 뷰로, 처리 대기 큐와 처리 완료 기록을 기록합니다. 이런 운영 흐름을 직접 `wiki/index.md`에 쌓지 않습니다.

## 로그 규칙

`wiki/log.md`는 타임라인이며, 토론 공간이 아닙니다.

각 로그는 다음과 같은 통일된 제목 형식을 권장합니다:

`## [YYYY-MM-DD] 동작 | 제목`

선택 가능한 동작:

- `init`
- `ingest`
- `approve`
- `query`
- `lint`
- `refactor`

로그 본문은 간결하게 다음을 기록합니다:

- 이번에 처리한 내용
- 새로 추가하거나 업데이트한 페이지
- 충돌이나 할 일이 발견되었는지 여부

## 명명 규칙

- 파일 이름은 간결하고 안정적이며 재사용 가능한 것을 우선합니다.
- 같은 개념에 대해 여러 유사한 파일 이름을 만들지 않습니다.
- 소스 요약 페이지라면 파일 이름에 소스 주제를 보존할 수 있으며, 날짜 접두사를 강제할 필요는 없습니다.
- 이름 변경이 필요한 경우 링크와 인덱스를 동기화하여 수정합니다.

## 금지 사항

- 확인되지 않은 추측을 사실로 작성하지 않습니다.
- "깔끔하게 정리한다"는 이유로 원본 자료를 삭제하지 않습니다.
- 본문만 업데이트하고 `wiki/index.md`와 `wiki/log.md` 관리를 잊지 않습니다.
- wiki만 업데이트하고 `raw/index.md`와 raw 파일 상태 관리를 잊지 않습니다.
- 사용자 확인 없이 `pending_review` 상태의 raw 파일을 `processed/`로 이동하지 않습니다.
- 보기 좋게 만들기 위해 충돌 정보를 삭제하지 않습니다.
- `wiki/`에 구조 없는 대량의 채팅 기록을 쌓지 않습니다.
- 외부 URL을 지식 그래프의 주요 관계 엣지로 사용하고 로컬 소스 페이지를 무시하지 않습니다.
- 사용자가 분류 서브폴더를 조정했다고 해서 이를 링크 오류나 구조 이상으로 잘못 판단하지 않습니다.

## 기본 동작

- 기본적으로 단일 처리는 하나의 ingest 단위; 이 단위는 단일 파일일 수도, 소규모 배치일 수도 있습니다.
- 기본적으로 작은 단계 업데이트를 우선하여 wiki의 검토 가능성을 유지합니다.
- 기본적으로 Markdown을 사용하며 추가적인 복잡한 시스템을 도입하지 않습니다.
- 기본적으로 Obsidian 이중 링크를 주로 사용하고 외부 데이터베이스에 의존하지 않습니다.
